# 10. Experimental Implementation and Results

The evaluation design of Section 9 is complete for all four questions, and its implementation status differs between them. This project completed Level 1 of the modeling stage, the compulsory level: the modeling strategy of Section 8 and the evaluation design of Section 9. The optional Level 2 prototype, a predictive experiment for AQ3 and AQ4, was specified in full in Milestone 4 as a protocol and has not been run (Milestone 4, Section 7). No model has been trained, so no model performance, metric, chart or confusion matrix exists for AQ3 or AQ4; their expected outputs are described in Section 11.4. Leaving the prototype unrun is our choice of scope, for two reasons. The brief makes Level 2 optional, so Level 1 completes the modeling stage. In addition, the 13 runs of 2014 are the project's only independent test and can be used once: we keep them for one complete run of the frozen protocol, from the baselines to the logged test, so that no 2014 result is seen before the model is frozen, and a partial early run would spend that test.

**What was computed instead.** In Milestone 5 we ran the AQ1 and AQ2 analyses on the 9 runs of 2013, following the methods and criteria that Milestone 4 fixed before any result. These are descriptive and diagnostic analyses, grouped rates with intervals and an association model, not the Level 2 modeling prototype: they train no predictive model, open no 2014 outcome and make no claim about how well non-completion can be predicted. Their results are reported with the findings, in Section 11.2 for AQ1 and Section 11.3 for AQ2, and their methods are those of Section 8.1. On the brief's scale the project therefore stands at Level 1: the AQ1 and AQ2 analyses are the analysis results of this report, not a Level 2 experiment.

**What the prototype specification fixes.** The protocol leaves the person who implements it no modelling choice of their own: every choice was fixed before any result existed, so the prototype can confirm or refute the choices of Level 1 but cannot reshape them after its results. A result that argues for a different primary approach, predictor set or criterion would be recorded as a new entry of the Controlled Change Log, with the frozen proposal shown beside it, and a baseline that matches the candidate is an acceptable outcome that would be carried forward with its reasons. The prototype tests feasibility and trade-offs, not the best attainable score. Table 10.1 gives the configurations it would compare.

**Table 10.1. Configurations of the specified prototype**

| ID | Role | Method | Predictors |
| :---- | :---- | :---- | :---- |
| B1 | Baseline | Random list | – |
| B2 | Baseline | Early-sign rule (C10), ranked by number of signs, ties by lower activity ratio | Rule columns |

Ties between configurations go to the simpler one. The protocol runs in eight steps: it reproduces the data input from OULAD-N04-prepared-1.0, checks every file against the hashes of the version manifest and stops on any mismatch; it fits the baselines first; it fits the candidates; it applies the split and folds of Section 9.1; it evaluates every configuration, reporting unfavourable results, including a baseline that matches or beats the primary model; it runs the error and subgroup analysis of Section 9.2; it compares the outcome with the Level 1 proposal; and it records scripts, seeds, package and data versions, folds and the test-access record in an experiment log. The model-ready matrices of the prepared dataset are not model input, because the protocol refits every transform inside each fold with deviation-coded modules (Section 7.1).

**One logged test.** The 2014 outcomes would be opened once, after the second freeze, with the access time and the hash of the frozen model written to the experiment log before any test metric is computed. Synthetic data may only test code paths, are labelled as synthetic and never feed a result. The outputs have fixed columns, covering the development folds, the model choice, the freeze, the test runs, the gate S1, the secondary metrics, calibration, fairness, the sensitivity analyses and the AQ2 replication on 2014; a column that does not apply holds an empty value, never a guess. The experiment log would record, for each run, the time in UTC, the command, the code commit, the exit status, the package versions, the prepared-data hashes, the random seeds, the folds and the test-access record.

**What would change in this report.** If the prototype runs, the project record changes in four places only: the results part and its appendix, the verdict of the comparison with Level 1, the Change Log only if a choice changes, and the AI Decision Log; every other section stays as frozen. Section 11 turns to the findings that the project has reached and to the expected outputs of the questions that wait for this test.
